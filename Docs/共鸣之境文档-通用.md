## 热门教程

### Terminology

本文档中会频繁出现一些你可能不熟悉的词汇和说法，这里给出简要解释。

- **GameData**：一个 *ScriptableObject*，包含大量本作前端设置，可轻松调整以满足需求并为游戏换皮。选项从是否显示血液的简单开关，到武器和游戏模式信息一应俱全，位于本作的 **Resources** 文件夹中。

更多信息请查看 **GameData** 章节。

- **Player Prefab**：构成本作玩家控制器的预制体，包含所需的全部脚本、对象和层级结构，
默认位于本作的 **Resources** 文件夹中。

更多信息请查看 **玩家预制体** 章节。

- **FPWeapon**：即**第一人称武器**，指本机玩家相机中看到的武器，也称**视图模型**。它与*第三人称武器*的区别在于包含武器本体和手臂或手部模型，且仅本机玩家相机可见。
 
第一人称武器位于每个玩家预制体的 **Local** 子节点内。

- **TPWeapon**：即**第三人称武器**，指其他玩家的士兵模型上看到的武器，也称**世界模型**。它与*第一人称武器*的区别在于只是单个武器模型，放置在玩家或士兵模型的双手之间。
 
第三人称武器位于每个玩家预制体的 **Remote** 子节点内，具体在玩家模型的右手骨骼上。

- **Unity 顶部菜单**：指 Unity 编辑器顶部的菜单项，***File、Edit、Assets、GameObject、Components、游戏设置等…***

### 如何修改框架

这个问题听起来像是修改本作会受到某种限制，但事实并非如此。只要清楚要做什么、知道怎么做，理论上没有任何限制，本作包含游戏的完整源代码和资源，一切都可以按开发者意愿修改。
 
本指南旨在给出修改本作的理想方式建议，**以便将来合并本作更新时轻松许多。**
 
如果使用本作已有一段时间，你会知道它最大的问题之一就是更新合并。每个大版本更新都需导入到新的 Unity 工程，因为把新版本导入到已有旧版本本作的工程中，会丢失此前对游戏所做的全部修改，而且极可能直接搞坏游戏。因此在旧版本工程中应用新版本的改进和修复，唯一可行的办法就是手动合并，逐个脚本检查、逐个预制体比对，堪称噩梦。
 
这在一定程度上源于本作的创建方式。由于代码硬编码和引用关系盘根错节，修改代码的唯一途径就是直接改游戏的默认脚本；
另外与工具类或扩展类素材不同，游戏模板本就预期用户或开发者去修改核心内容，这也加剧了升级到新版本的难度。
本作的后端设计已按继承方式重做，大部分代码支持继承，开发者无需修改默认脚本即可改代码，只需新建一个脚本 ➔ 继承自基类 ➔ 实现自己的改动。
 
下一页会详细介绍这一点以及如何使用这类代码设计。

**代码修改**

大部分默认脚本采用代码继承设计，**继承允许你或你的程序员基于游戏已有的类创建新类，在保持行为一致的前提下指定新的实现，实现代码复用，并独立扩展原有代码。**
 
**以下举例说明这种设计如何工作、有何帮助：**
 
在早期版本中，若想修改武器拾取系统，必须直接改 **GunPickUp.cs** *（默认脚本）*，这会导致该脚本无法再自动更新，否则你的改动就会丢失。
而在当前版本中做同样的修改，无需直接改默认脚本，而是新建一个脚本并继承其基类（本例为 **GunPickUpBase**）➔ 把默认脚本的代码复制到新脚本中，然后做想要的修改。由于所有引用都指向基类，无需担心引用问题，只需在原本挂载默认脚本的物体上换挂你的新脚本，并移除或卸载默认脚本即可。
 
**如何继承脚本？**
 
若你是有中高级经验的程序员，可能已熟悉这种编程设计，它不仅是优秀代码的应有之义，也让代码更易维护和扩展，并带来多态结构，从而以更少代价实现新功能或变体。
 
若你不是程序员或不熟悉代码继承，做法很简单：以武器拾取为例新建一个脚本，假设该脚本用于修改武器拾取逻辑，创建后其结构大致如下：

```
using UnityEngine;
 
public class GunPickUp2 : MonoBehaviour
{
    ...
}
```

接下来要修改基类*（紧随你的类名之后那个类名）*，此处原为 MonoBeheaviour，需改为 *GunPickUp* 的基类 GunPickUpBase，结果如下：

```
using UnityEngine;
 
public class GunPickUp2 : GunPickUpBase
{
    ...
}
```

> 几乎所有默认脚本的基类都遵循同样的命名规则，只是在名称末尾加上 "Base" 一词。不过要确认某个脚本的基类，最可靠的方法还是打开该默认脚本查看。

改好基类后，需要重写基类的函数或方法。若不知如何操作，直接把原类*（本例为 **GunPickUp.cs**）*的代码复制粘贴到你的脚本中即可，
这样就够了，之后便可在新脚本中做任意修改。

如前所述，这并非修改代码的强制要求，而是推荐做法。本作并非所有代码都支持继承，目前已有超过一半代码按此方式重做，但工作仍在进行，目标是让全部或至少大部分代码支持继承并在未来更新中保持模块化。

*代码修改*的同一思路也适用于预制体、菜单、场景等其他游戏内容的修改。
**理想做法是不修改默认内容，而是创建副本**并使用副本，例如：
对于 MainMenu 场景，应创建该场景的副本，保留默认场景原样以备将来参考。
这样将来合并本作更新时，导入后不会丢失你在该场景上的修改，且保留原场景可作为参照，对比新版本在该场景中做了哪些改动。
 
玩家预制体同理，不要使用默认玩家预制体*（Player [BLUE] 和 Player [RED]）*，而应为每个创建副本并使用这些副本*（在 GameData 中指定）*。
 
道理就是这样，不要使用默认内容 ➔ 创建并使用副本。

> 在编辑器中，几乎任何内容都可以通过以下方式复制：在 Project 视图中选中它，Windows 上按 **Ctrl + D**，Mac 上按 **Command + D**。

### DrawPhotonPun

**Photon Unity Networking** 简称 **Photon PUN** 是本作用来处理所有网络与服务端事务的网络方案，它是 Unity 领域最扎实的解决方案之一，速度快、稳定、可扩展，符合你对通用网络方案的预期。PUN 在全球提供多个服务器节点，你可以连接到延迟最低的那个。

在 Unity 中 PUN 以第三方插件形式提供，可在 Unity 资源商店免费下载 ***按照「快速开始」教程操作你多半已经下载过了***。
关于这套网络方案有一些常见疑问。首先，服务端事务必然产生成本，PUN 承担了全部服务端工作，包括代码、托管、运维、扩容、服务器维护等，这些都不用你操心，Photon 团队会处理。但正因为存在服务成本，**PUN 是付费服务**，同时提供免费套餐供开发阶段使用，正式发布前再升级即可。

你可以在其官网查看所有可用套餐：
Photon PUN 套餐（https://www.photonengine.com/en-US/PUN/pricing）

我经常收到的一个问题是：

***那权威服务器呢？***

如果你此前接触过网络系统，可能已经注意到 Photon 使用一个客户端 *称为 Master Client* 而非服务器 *Master Server* 来裁定游戏逻辑。这给作弊者留下了空间，他们可以在自己的客户端上修改玩法并同步给其他客户端，因为没有独立的 Master Server 来比对和校验逻辑。

开箱即用的 Photon PUN 并没有针对这个问题的完备方案，官方给出的是 Photon OnPremise（https://www.photonengine.com/en-us/Server） 即 Photon Server。用它你可以自行托管服务端代码与 SDK，通过修改服务端代码打造自己的权威服务器，但这需要相应的技术积累。如果你对 Photon Server 感兴趣，下一节有更多说明。

如上一节所述，**Photon Server 是 Photon PUN 的替代方案**，它有一些优势，也有需要权衡的地方。相比 Photon PUN，使用 Photon Server 的好处包括：
 
- 自托管服务器，对服务端代码有更强控制力。
- CCU 套餐价格更实惠，并提供不限量套餐。
- 可以在 PUN 不覆盖的特定区域部署服务器。
- 整体成本低于 Photon PUN 套餐。

但使用 Photon Server 时必须考虑以下问题：
 
- 服务器的持续运行由你负责，崩溃、停机、清理等都要自行处理。

- 可用区域取决于你把服务器托管在哪里。Photon PUN 可以轻松切换全球 13 个以上的区域，而 Photon Server 只有你托管的那一个区域，除非你在游戏里另外做一套服务器选择系统。

- 扩展性取决于你的托管类型和套餐。Photon PUN 需要更多 CCU 时直接升级套餐即可，Photon Server 即便使用不限量 CCU 套餐，如果托管服务器本身不支持自动扩容，游戏规模增长就会遇到瓶颈。因此推荐使用 AWS EC2 这类可弹性伸缩的服务器方案。

Photon Server 的详细资料见官方页面：
https://doc.photonengine.com/en-us/server/current/getting-started/photon-server-intro（https://doc.photonengine.com/en-us/server/current/getting-started/photon-server-intro）

**在本作中使用 Photon Server**
 
在本作中使用 Photon Server 替代 Photon PUN 不需要改动本作代码，但需要手动配置服务端 SDK，这需要一定的经验。好在官方文档对搭建和部署自有服务器的流程讲解得清晰且步骤完整，指南见此处：
https://doc.photonengine.com/en-us/server/current/getting-started/photon-server-in-5min（https://doc.photonengine.com/en-us/server/current/getting-started/photon-server-in-5min）

Photon Server SDK 搭建并运行起来之后，项目里只需做几件事即可开始使用：
 
- 在本作的 Unity 项目中打开 PhotonServerSettings 点击此处，其默认位置在 *Assets ➔ Required ➔ Photon ➔ PhotonUnityNetworking ➔ Resources ➔ PhotonServerSettings*。

- 展开 **Server/Cloud Settings**，取消勾选 **Use Name Server**。

- 在 **Server** 文本框中填入服务器 *即你部署 Photon Server SDK 的位置* 的公网 IP 或域名。
 
- 在 **Port** 输入框中填写你为服务器开放的端口号，若未改动则使用默认值：**UDP 为 5055**，**TCP 为 4530**。
 
完成以上设置后，若配置正确，游戏应当能正常运行并连接到你的服务器。

**什么是 CCU？**
 
**CCU** 是 **Concurrently Connected Users** 的缩写，即同时在线用户数。在 Photon 及其他网络插件中，它指服务器或套餐允许的同时在线玩家上限。
 
Photon PUN 的每个套餐都有 CCU 上限，达到上限后会拒绝新连接，新玩家必须等到有位置空出才能进入。用于开发调试的默认套餐上限为 20 CCU，即最多 20 名玩家同时在线。

> 不要把 **CCU** 与 **DAU** *日活跃用户* 或 **MAU** *月活跃用户* 混淆，CCU 只统计同一时刻在线的玩家。

**如何判断自己需要多大的 CCU 上限？**
 
Photon 套餐的 CCU 上限越高，月费越贵，因此选对套餐很重要。可以依据 CCU 与 DAU、MAU 之间的平均比例关系推算：根据你的游戏日活或月活玩家数量，就能大致判断需要多大的 CCU 套餐。

> 这些数据取自 Photon 官方统计，覆盖了大量使用 Photon 的游戏作品。

CCU 到 DAU 的系数为 10 到 100 之间，视游戏而定。
DAU 到 MAU 的系数为 10。
 
所以 **100 CCU 可能足以支撑多达 10 万月活用户**。
刚上线、初期关注度和在线时长都很高的新游戏会明显偏离这些数值，因此这些系数并不固定。

### Offline

本作支持 Photon **离线模式**，可以直接运行地图场景进行测试，无需经过进入大厅、创建房间、加载地图场景的流程。

当你修改了玩家预制体或武器并想立刻在运行时验证时，这个功能尤其省事，能节省大量时间、提升开发效率。

开关位置在 **GameData** -> Offline Mode。
启用后直接打开地图场景点运行即可。

> 离线模式**并非**用来借助本作开发单机游戏，它的目的是方便多人在线玩法的开发调试。

创建通用渲染管线资源
通用渲染管线资源控制项目的全局渲染与画质设置，并创建渲染管线实例。渲染管线实例包含中间资源与渲染管线实现。

将通用渲染管线资源加入图形设置的方法：

在 **Scriptable Render Pipeline Settings** 字段中加入之前创建的通用渲染管线资源。加入后图形设置会立即变化，项目即开始使用 URP。

### HDRP

HDRP 是 Unity 面向高端平台的新渲染管线之一，可以调用前沿的实时 3D 渲染技术，提供高保真画质与不妥协的 GPU 性能。本作默认使用内置渲染管线，你也可以手动把项目转换为 HDRP，本指南说明具体做法。

**将本作转换为 HDRP**
 
本教程假定你的本作项目基于内置渲染管线，Unity 版本为 2020.1 或更高。教程中提到的部分选项在新版编辑器中位置或名称可能不同，遇到这种情况可查阅对应 Unity 版本的官方指南：
https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Upgrading-To-HDRP.html（https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Upgrading-To-HDRP.html）

配置渲染管线之前必须先移除 **Post Processing** 包，因为 HDRP 不支持它，HDRP 自带了后处理系统。可在 Unity 包管理器（Window > Package Manager）中移除 Post Processing 包，等待脚本重新编译完成后继续下一步。

**配置 HDRP**

首先为 Unity 项目添加 High Definition RP 包以安装 HDRP：
 
<?list=•>打开 Unity 项目。

在包列表中选择 **High Definition RP**。
点击包管理器窗口右下角的 **Install**。

> *注意：* 安装 HDRP 后，Unity 会自动为场景中的 GameObject 附加两个 HDRP 专用组件：为灯光附加 **HD Additional Light Data**，为相机附加 **HD Additional Camera Data**。如果项目未设置为使用 HDRP，而场景中又存在 HDRP 组件，Unity 会报错。要解决这些错误，按下面的说明在项目中配置 HDRP。

在项目中配置 HDRP 请使用 HDRP 向导（https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Render-Pipeline-Wizard.html）。
 
通过 **Window > Rendering > HD Render Pipeline Wizard** 打开 **HD Render Pipeline Wizard** 窗口。
在 **Configuration Checking** 区域切到 **HDRP** 选项卡，点击 **Fix All**，这会修复项目全部 HDRP 配置问题。
配置问题修复之后场景可能仍渲染不正常，因为场景中的 GameObject 依然在使用内置渲染管线的着色器。内置着色器升级为 HDRP 着色器的方法见下一步的「升级材质」。

**升级材质**

将场景中的材质升级为 HDRP 兼容材质的方法：
 
1. 打开 **Edit > Rendering > Materials**
2. 选择以下选项之一：
 
 ■ **Convert All Built-in Materials to HDRP**：把项目中所有可转换的材质转为 HDRP 材质。

 ■ **Convert Selected Built-in Materials to HDRP**：把 Project 窗口中当前选中的可转换材质转为 HDRP 材质。

 ■ **Convert Scene Terrains to HDRP Terrains**：把场景中每个地形的内置默认标准地形材质替换为 HDRP 默认地形材质。

**限制**

上述自动升级选项无法把所有材质都正确转换到 HDRP：
 
自定义材质与着色器无法自动升级，必须手动转换。本作中的水面着色器属于自定义着色器，无法自动升级，你需要把它替换为 HDRP 水面着色器，或者从场景中移除水面。

使用高度图的材质可能显示异常。原因是 HDRP 支持的高度图置换技术与压缩选项比内置渲染管线更多。要升级使用高度图的材质，请调整材质的 Amplitude 与 Base 属性，直到效果尽量接近内置渲染管线下的表现。

**粒子着色器无法升级**。HDRP 不支持粒子着色器，但提供了与内置粒子系统兼容的 Shader Graph。这些 Shader Graph 的工作方式与内置粒子着色器类似。要使用它们，请导入 Particle System Shader Samples 示例：
 
 1. 打开 **Package Manager** 窗口，菜单为 **Window > Package Manager**。
 2. 找到并点击 **High Definition RP** 条目。
 3. 在 **High Definition RP** 的包信息中进入 **Samples** 区域，点击 **Particle System Shader Samples** 旁的 **Import into Project** 按钮。

**调整光照**

HDRP 使用 物理光照单位（https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Physical-Light-Units.html） 控制灯光强度，这些单位与内置渲染管线使用的任意单位并不对应。
 
就光强单位而言，平行光使用 Lux，其余灯光类型可使用 Lumen、Candela、EV，或模拟特定距离处的 Lux。
 
在 HDRP 项目中配置光照的步骤：
 
1. 为场景添加默认天空 Volume 并配置环境光，操作路径为 **GameObject > Volume > Sky and Fog Global Volume**。

2. 让 环境光照（https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Environment-Lighting.html） 使用这个新天空：
 
 - 打开光照窗口，菜单为 **Window > Rendering > Lighting Settings**。
 - 在 **Environment** 选项卡中，把 **Profile** 属性设为 Sky and Fog Global Volume 所用的同一个 Volume Profile。
 - 把 **Static Lighting Sky** 属性设为 **PhysicallyBasedSky**。
 - 可选：如果不想让 Unity 在本节后续改动时重新烘焙场景光照，可以取消勾选窗口底部的 **Auto Generate**。

3. 当前阴影画质偏低，提升阴影画质的方法：
 
新建一个 **Global Volume** GameObject，菜单为 **GameObject > Volume > Global Volume**，命名为 **Global Settings**。
为该 Global Volume 新建 Volume Profile：
 
 - 打开 Global Volume 的 Inspector 窗口，找到 Volume 组件。
 - 进入 **Profile**，选择 **New**。
 - 添加阴影覆盖项：
 
  - 进入 Add **Override > Shadowing > Shadows**。
  - 启用 Max Distance。
  - 把 Max Distance 设为 50。

4. 配置代表太阳的灯光 GameObject。
 
 - 在场景中选中代表太阳的 Light GameObject，在 Inspector 中查看。
 - 进入 **Emmision**，把 Intensity 设为 100000。
 - 把 **Light Appearance** 设为 **Color**。
 - 把 **Color** 设为白色。
 - 若要在天空中看到太阳，进入 **Shape**，把 **Angular Diameter** 设为 3。

5. 此时场景会过曝，修正方式如下：
 
 - 选中第 3 步创建的 **Global Settings** GameObject。
 - 为其 Volume 组件添加 **Exposure** 覆盖项，菜单为 Add **Override > Exposure**。
 - 启用 **Mode** 并设为 **Automatic**。
 - 若需刷新曝光，进入 Scene 视图并启用 **Always Refresh**。

最后还需要手动为所有本作玩家预制体配置相机堆叠：
 
1. 在预制体编辑器中打开玩家预制体，或把其拖入场景层级。
 
2. 在玩家预制体层级中，选中位于 **Local > Mouse > Animations > Main Camera > WeaponCamera** 的 **WeaponCamera**。
 
3. 在 **Camera** 组件的 Inspector 窗口中展开 **Output** 选项卡，把 **Depth** 设为 2。
 
应用并保存玩家预制体的改动，对游戏中其余所有玩家预制体重复此流程。全部完成后，项目向 HDRP 的基础转换就完成了。

### AntiCheat

作弊是游戏开发者迟早要面对的问题，在竞技类多人游戏中尤为突出。你不得不应对那些试图利用漏洞获取优势的修改者和作弊者。因此从项目一开始就要采取防护措施。
 
本作默认不包含任何反作弊系统，因为这类系统体量大、复杂度高，其价值本身就超过本作的价格。本作内置了第三方反作弊资源的基础集成，可解决当下大多数常见作弊手段，该资源为资源商店中的
Anti-Cheat Toolkit (ACTk)（https://assetstore.unity.com/packages/tools/utilities/anti-cheat-toolkit-2021-202695?aid=1101lJFi）
借助它可以阻止玩家修改生命值、弹药、掉落物、金币等数据。
 
本作只包含能阻止玩家修改这些数值的基础集成。如需自动封禁使用加速、内存注入、代码注入或穿墙类作弊的玩家，需要另行接入第三方反作弊方案。
 
这能劝退大多数业余作弊者，但对经验丰富的修改者仍不够。事实上没有绝对无法破解的程序，你只能不断提高门槛让对方放弃。基于这一点，以下还有若干实现与调整可以让你的游戏在各平台上更安全：

**1. 使用 IL2CPP**
 
Unity 目前支持两种脚本后端：**Mono** 与 **IL2CPP**，后者更新也更安全。IL2CPP 生成的是带元数据的原生二进制代码，而非 Mono 的 IL 字节码，所有 IL 反编译工具都会失效，想得到可读性好的游戏代码反编译结果会难上加难。
 
该功能 Unity 内置，只需在 **Project Settings > Player > Scripting Backend** 中切换脚本后端。
 

**2. 代码混淆**
 
代码混淆是在构建过程中为脚本参数、函数、属性等随机生成名称，使反编译出的二进制代码几乎无法阅读。代码会变成一堆无意义名称的组合，重建出的 IL 程序集极难逆向分析。
 
遗憾的是 Unity 并未内置该功能，需要借助第三方方案。Unity 生态中最流行且易用的混淆器可在资源商店获取：
Obfuscator（https://assetstore.unity.com/packages/tools/utilities/obfuscator-48919?aid=1101lJFi）

**启用反作弊**
 
启用反作弊集成的方式：若使用插件进行进阶集成，请参照插件文档；若未使用插件但已安装 Anti-Cheat Toolkit 资源，想启用本作中的基础集成，则进入编辑器顶部菜单 Tools > Code Stage > Anti-Cheat Toolkit > Settings... > Conditional Compilation Symbols，勾选 **ACTK_IS_HERE** 即可。

### DrawCoins

本作内置虚拟货币系统，包含两种货币：一种通过游戏获得 *随经验值*，另一种只能用真实货币购买 *通过你自建的内购实现*。
 
无需改动代码即可自定义货币的大量属性，例如 **货币名称、颜色、图标和面值**。
 
修改这些属性请进入 GameData ➔ Game Coins ➔ 展开要修改的货币。多数属性名已能自解释，以下说明容易混淆的几个：

- **Acronym**：货币名称的缩写。

- **Coin Value**：货币相对于 1 的面值。举例说明：假设某武器的游戏内标价为 100，若该货币面值为 0.25，则玩家需要 400 枚该货币才能购买 *0.25 = 1/4，故 400/4 = 100*；若面值为 2，则只需 50 枚。
 
这样设计的目的是：你只需为游戏内物品设置一个标价，各货币对应的实际数量由游戏自动换算。

- **Initial Coins**：新玩家首次进入游戏时获得的该货币数量。

**如何使用这些货币？**

 
本作默认不将货币用于任何用途，怎么用由你决定：可用于购买武器、特殊皮肤、干员等游戏内物品，也可实现开箱系统，或任何你能想到的玩法。
 
若想实现商店系统、让玩家购买武器与货币包，或接入支付系统以支持真实货币购买，需要自行实现或另行接入相应方案。

若要对玩家钱包执行 **增加** 或 **扣减** 指定数量货币这类基础操作，一行代码即可完成：
 

**增加货币**


### GameModes

本作提供 3 种游戏模式：**团队死斗、夺旗和自由混战**，各自逻辑位于独立脚本中，路径为 *Assets/Scripts/GamePlay/GameModes ➔ **。
 
各模式都有一些通用属性可在 GameData ➔ Game Modes ➔ * 的检视面板中调整，展开任一模式即可看到全部可配置项。

各项含义如下：

- **Mode Name**（string）：该模式的名称，用于游戏内显示。

- **Game Mode**（enum）：该模式的内部标识，用于在代码中识别特定模式。Game Modes 列表中不允许存在标识相同的模式。

- **Is Enable**（bool）：该模式是否在游戏中可用。

- **Support Bots**（bool）：是否可创建该模式的房间并加入机器人？**注意：**默认情况下仅 TDM 与 FFA 模式支持机器人。

- **自动分配阵营**（bool）：是否强制自动分配阵营以保持双方人数均衡？

- **开始所需玩家数**（int）：该模式下开始游戏所需的最小加入人数。

- **回合中途加入时的出生方式**（enum）：在该模式的房间中，回合已开始后玩家加入时如何处理。

- **玩家死亡时**（enum）：该模式下玩家死亡后发生什么。

- **Goal Name**（string）：该模式中计分目标的名称，例如击杀、夺取、得分等。

- **允许拾取武器**（bool）：该模式下玩家能否拾取武器。

- **Max Players**（int[]）：该模式可选的最大玩家数，这些选项会出现在大厅的创建房间菜单中。

- **游戏目标选项**（int[]）：该模式目标的可选值，如击杀数、夺取数、分数等，这些选项会出现在大厅的创建房间菜单中。

- **Time Limits**（int[]）：该模式可选的对局时长，单位为秒，这些选项会出现在大厅的创建房间菜单中。

除本作内置的 3 种模式外，还有更多热门模式可以扩展实现，例如 ***爆破拆除、占点模式、枪战竞速、淘汰模式和确认击杀***。

这个问题不好一概而论，因为每个模式的需求、逻辑和玩法都不同，做法自然各异。因此我无法直接教你如何从零设计模式，但可以告诉你怎么把它接入本作。

```
        }
```

### MouseLook

视角控制即鼠标视角与相机控制是射击游戏或任何快节奏动作游戏的核心功能。
 
本作采用了几种技术来提升视角移动的精准度与顺滑度，例如 **帧平滑** 与 **移动平滑**。
 
若要个性化该运动，可在检视面板中修改若干属性：
 
通用设置位于 GameData -> Mouse Look Settings。

- **Use Smoothing**（bool）：是否启用帧平滑。该技术通过计算过去若干帧鼠标移动的平均值，让视角移动更顺滑。

- **平滑帧数**（int）：参与平均值计算的缓冲帧数。数值越大越顺滑，但精度越低。

- **Lerp Movement**（bool）：是否为移动额外叠加一层平滑。适合触屏设备，不推荐用于鼠标或手柄操作。

- **瞄准灵敏度调整方式**（enum）：决定鼠标灵敏度如何过渡到瞄准灵敏度。**Fixed** 表示直接采用瞄准灵敏度的确切值，**Relative** 表示按相机视野变化量换算。

**逐玩家属性**

还有一些属性可以按玩家分别设置，位置为玩家预制体 ➔ FirstPersonController ➔ Mouse Look ➔ *，

**灵敏度**

玩家可以在游戏内调整鼠标或手柄灵敏度，但默认值由你设定，位置为 GameData ➔ Default Settings ➔ Settings Values ➔ **Sensitivity** 与 **Aim Sensitivity**。

### DrawObjectPooling

**什么是对象池？**

**Instantiate()** 与 **Destroy()** 是游戏运行中常用且必要的方法，单次调用消耗的 CPU 时间通常很少。

但对于运行期创建、生命周期短、每秒销毁数量巨大的对象，例如子弹，CPU 需要花费的时间就相当可观。

这正是对象池发挥作用的地方。**对象池** 指在游戏开始前预先实例化所有可能用到的对象。本作中子弹、弹痕和命中粒子都使用对象池。

ObjectPooling.cs 使用起来很简单。把对象加入池中只需在 ObjectPooling 检视面板的 **pooledPrefabs** 列表中登记该预制体，该脚本挂在各地图场景的 **GameManager** 对象上。加入预制体后设置一个池化名称，再估计需要多少个实例即可。

在脚本中取用该预制体时，原先通常写法如下：

```
GameObject ob = Instantiate(MyPrefab, position, rotation);
```

使用 ObjectPooling 后，替换为：

```
GameObject ob = ObjectPooling.Instance.Instantiate("PrefabKey", position, rotation);
```

### GameInput

射击游戏 **或者说所有游戏** 的一个关键要素是操作控制。在动作游戏中这一点尤其特殊，因为玩家往往有自己习惯的按键设置。本作默认采用多数 FPS 游戏通用的标准按键方案。
 
本作内置了自定义输入管理器，可在运行时通过设置窗口中的菜单重新绑定按键。你可以在 *Input Mapped* 中定义默认按键，是否允许玩家在游戏内修改由你决定。
 
如果你想使用第三方输入管理器，本作同样支持。游戏中使用的全部输入都定义在 GameInput.cs 脚本中，修改这些函数中的代码即可指向你自己的输入系统。
 
通过函数名即可判断某个输入对应哪个游戏动作 *开火、装弹、跳跃等*。

要修改键盘或手柄的默认按键映射，只需改动对应的映射资源。

选中该映射 ScriptableObject，若使用的是默认资源，其位置为 *Assets ➔ Prefabs ➔ Presents ➔ Input Mappeds➔**。选中后在检视面板中可看到全部已配置的输入项，展开要修改的项并编辑其中的信息 *按键码、轴名称、描述等*。

你还可以调整输入项的排列顺序，列表顺序即游戏内的显示顺序。

新增输入很简单，基本只需在输入映射中加一项并设置按键码。

1 - 选中要新增输入的映射资源。默认只有两个：Keyboard 与 Xbox Controller，选择你要修改的那个，其位置为 *Assets ➔ Prefabs ➔ Presents ➔ Input Mappeds➔**。

2 - 在该映射的检视面板中会看到名为 **Button Map** 的列表，其中是当前全部输入项。在列表中新增一项并填写信息：

- **KeyName**（string）：该输入的自定义按键名称

- **PrimaryKey**（KeyCode）：该输入对应的 Unity 按键码

- **PrimaryAxis**（string）：若该输入对应的是轴而非按键，在此填写轴名称。

按键配置完成后即可在代码中使用，用法与 Unity 默认 Input 非常接近。原先写法为：

```
Input.GetKeyDown('keyName'){...}
```

现在改用：

```
InputHandler.isButtonDown('keyName'){...}
```

or

```
InputHandler.isButton('keyName'){...}
InputHandler.isButtonUp('keyName'){...}
```

其中 *keyName* 的值是你为该输入在 Input Mapped 中设置的 **KeyName**。

要在本作与输入管理器中用手柄，需要额外几步操作。
 
- 首先，若安装本作时 *在安装窗口里* 没有覆盖输入设置，你需要修改 Unity 输入设置以添加所需的控制轴。输入管理器附带了一份已配置好的 **Input Settings.asset**，点击下方按钮即可应用。

在 InputManager 的 **Mapped** 字段中指定你的手柄对应的输入映射。默认附带 Xbox 手柄的映射，把该映射或你自建的映射拖入 **Mapped** 字段即可

新建输入映射的方法：在 *Project 视图* 中进入目标文件夹 -> 右键 -> Create -> 游戏设置 -> Input -> Input Mapped，随后即可看到新建的资源对象，选中它并配置你的手柄或键盘的全部输入。

也可以直接复制一个默认映射再修改其中的输入项。

### Doors

本作内置一套经过优化的门系统，可为地图增添动态元素。
 
该系统针对单张地图门数量较多的情况做了性能优化，支持网络同步，使用也很简单。
 

**如何添加门？**

 
- 给地图添加一扇门只需两步：
 
**1. 在地图中放置门：** 把门预制体拖入场景层级并按设计摆放。默认门预制体为 default door prefab，位于 *Assets ➔ Prefabs ➔ Level ➔ Items ➔ Door*。
 
**2. 注册新门：** 在地图场景层级中进入 ItemManager ➔ DoorManager ➔ 点击 **Collect all active doors in scene** 按钮即可。

**如何创建新门？**

 
- 若想使用自定义门模型，只需在默认 door 预制体基础上替换模型。
 
1. 在任意场景中实例化默认 door 预制体，并解除该实例的预制体关联 *右键该门的实例 ➔ Unpack Prefab Completely*。
 
2. 把自定义门模型拖入该实例的 Door ➔ Door Model ➔ * 下，并手动把新门模型的位置、旋转和缩放调整到与默认模型一致。
 
3. 选中该门实例的根节点 ➔ **BasicDoor** ➔ 在 **Door Pivot** 字段中拖入你新门模型的 Transform，该点将作为门的旋转轴心。
 
4. 删除默认模型 *Door ➔ Door Model ➔ **Default Door Model***，然后把门拖到 Project 视图的任意文件夹中保存为新预制体。
 
若门模型旋转不正确，新建一份 Door Settings *Project 视图 ➔ 右键 ➔ 游戏设置 ➔ Level ➔ Door Settings* ➔ 把它指定给门预制体的 BasicDoor ➔ **Door Settings**，并在其中设置新门模型轴心的旋转值。

### PlayerIK

### 事件 API

如果你想在自己的脚本中实现自定义功能或改动，可以使用一组特殊事件，例如本地玩家出生、本地玩家死亡、受到伤害等。

使用这些事件很简单，只需在脚本中订阅一个函数，运行时事件派发时即可收到回调。

```
void OnEnable()

private void OnDisable()

GameEvents.onLocalPlayerSpawn -= OnLocalPlayerSpawn;

void OnLocalPlayerSpawn()

//execute your code
}
```

### 版本更新

本作会持续更新，带来新功能、修复与改进。若你希望把上游的改进与修复同步进自己的项目，需要注意：受资源本身的性质限制，直接把新版本包导入到旧版本项目上会覆盖你所有的改动，导致此前的工作与进度全部丢失。

把旧版项目更新到新版本所需的工作量取决于多个因素，例如你改动了多少内容、项目所用版本与新版本的差距、新版本中变更的数量等。

下面针对不同情况给出更新版本的方法：

> **重要提示：在尝试以下任何方法或对项目做任何更新操作之前，务必先备份整个项目**

## 前端改动

- 如果你只做了前端改动，例如替换 *玩家模型、调整属性、添加地图、添加武器、修改 UI 等*，而未改动后端代码，更新就简单些：可以在现有项目上导入新版本包，只是需要 **取消勾选** 下列资源。

首先获取新版本的完整工程。

在 **Unity 包导入窗口** 中可以勾选要导入的资源，默认全部选中。为避免覆盖你的改动，只需 **取消勾选** 以下内容：

•  **Resources** 文件夹 *包含其中全部预制体与 GameData*
•  MainMenu 场景 *若你修改过 UI*
•  任何你改动过的预制体。

ExampleLevel 场景则要导入，因为它几乎肯定包含变更，可以作为你其他地图场景的参照。

## 后端改动

如果你对核心脚本做过 **代码改动**，或修改过 **GameManager、GameModes、Lobby 等** 主要预制体，更新流程就更复杂。

首先，无法直接在当前项目上导入新版本，因为这会还原你所有的改动、丢掉全部工作。要应用新版本的变更，必须手动合并：查看新版本中脚本与预制体的改动，再与自己的项目逐一比对。

这个过程耗时较长，而且合并失误很容易导致游戏报错。因此我给出一个能减少工作量的方法：

•  首先新建一个干净的 Unity 项目，在其中按常规方式导入新版本工程 *同时导入 Photon PUN*。这个项目作为参照，用来查看场景、预制体、属性等前端层面的改动。

•  然后在你的既有项目 *即修改过的旧版项目* 中 **模拟** 导入新版本工程。注意是 **模拟**，**不要真正导入**。你只需要让 Unity 包导入窗口弹出来，以便查看有哪些文件发生变化。该窗口会列出包中所有将导入的资源，若某个文件在项目中已存在，还会标明包内文件与项目内文件是否不同，这些有改动的文件右侧会显示一个 Refresh 图标：

接下来要做的是记录这些变动过的文件，把文件名写在一个简单的文本文件里，方便后面按名称查找。

收集好全部变动文件名之后就要开始合并。遗憾的是没有自动化方式，只能手动处理，逐一查看脚本、预制体等内容的改动。不过不必逐行核对，可以借助工具自动比对两个文件的差异。

比对脚本改动可以使用以下工具：

Standalone program: Diffmerge（https://sourcegear.com/diffmerge/）
Online System: Diffchecker（https://www.diffchecker.com/）

这两个工具用起来都很直接：有两个文本框，一个放入旧文件的内容，另一个放入新文件，程序会分析并高亮出有差异的行：

把原始文件 *即你项目中的那个* 放在左侧，新版本工程的文件 *即你之前新建项目中的那个* 放在右侧。

差异高亮出来后，只需把这些改动合并进你的项目文件 *即旧版工程的文件*。

使用独立程序 **Diffmerge** 还可以比对整个工程文件夹、分析所有文件，操作为选择 File -> Open Folder Diff... -> 在第一个框中填入旧版工程文件夹路径，第二个框中填入新版工程文件夹路径。

上述方法对脚本这类文本文件很高效，但比对预制体与场景的差异需要另想办法，得同时打开两个项目对比。好在 Unity 允许同时打开多个编辑器实例，因此可以把旧版项目与新版工程分别在不同编辑器窗口中打开，逐一检视两个项目中预制体与场景的差异。

### ServerRegion

Photon PUN 支持 **连接多个服务器区域**。本作实现了全部可用服务器，并让玩家自行决定是否连接特定区域。
 
默认情况下，Photon PUN 会根据玩家网络选择 ***最佳区域*** 连接。这对同时在线人数不多的游戏会造成问题：玩家被分散到不同区域，更难匹配到对局。因此本作定义了 **固定区域**，即所有玩家默认连接的区域，玩家如有需要也可以在游戏内手动切换到其他服务器。
 
**定义固定区域**
 
进入 MainMenu 场景 -> Lobby -> Lobby -> 在检视面板中找到 **Default Server** -> 选择作为默认连接区域的区域代码。
 
**运行时更换服务器区域**
 
玩家可在游戏内通过大厅菜单右下角的下拉框更换服务器区域。

### PlayerHitbox

受击盒是用于检测外部物体与玩家碰撞的基础形状碰撞体，通常为长方体、球体或胶囊这类简单形状。本作中它们位于玩家预制体模型的标准人形骨骼上。

### PlayerDamage

玩家默认会受到武器伤害、坠落伤害和载具碰撞伤害，这些伤害由玩家受击盒接收，或由 PlayerHealthManagerBase 脚本处理。
 
若要向玩家造成伤害，做法如下：
 
****对本地玩家造成伤害****
 
- 对本地玩家造成伤害可调用 **PlayerHealthManagerBase** 脚本的 **DoDamage(...)** 函数，该脚本挂在玩家实例的根节点上。
 
该函数需要 **DamageData** 参数，其中包含本次伤害的全部信息。
 
你还需要拿到目标玩家的引用。获取方式取决于你的伤害是如何触发的。例如用射线检测时，射线命中本地玩家后即可从该玩家取得 *PlayerHealthManagerBase* 引用，再调用 **DoDamage(...)** 并传入 **DamageData**，例如：

```
void DealDamageFunction()
    {
        if(Physics.Raycast(transform.position, transform.forward, out RaycastHit raycast, 10))
        {
            if (raycast.collider.isLocalPlayerCollider())
            {
                var playerReferences = raycast.transform.GetComponent<PlayerReferencesHandler>();
 
                DamageData damageData = new DamageData()
                {
                    Damage = 20, // base damage to apply
                    Direction = transform.position,
                    Cause = DamageCause.Player,
                    GameActor = GameCore.LocalPlayer.GameActor, // the actor that caused this damage
                    // Check the other DamageData properties
                };
 
                playerReferences.playerHealthManager.DoDamage(damageData);
            }
        }
    }
```

这样就完成了，上例会向目标玩家造成 20 点伤害。
 
如果你只是想立刻杀死本地玩家，直接调用 **GameCore.LocalPlayer** 中的 **Suicide()** 函数即可：

```
GameCore.LocalPlayer.Suicide();
```

以上方式只适用于本地玩家。若要对远程玩家 *即不由本地客户端控制的玩家* 造成伤害，做法如下

****对远程玩家造成伤害****

对远程玩家造成伤害只能通过其受击盒引用。受击盒是包裹玩家模型的碰撞体，上面挂有继承自 **HitBoxBase** 的脚本，其中包含 **ReceiveDamage(...)** 函数，调用它即可造成伤害。
 
你需要拿到目标远程玩家的受击盒引用。获取方式取决于你希望如何施加伤害。例如通过爆炸造成伤害时，检测爆炸原点一定半径内的碰撞体，伤害函数可以这样实现：

```
void DealDamageFunction()
    {
        Collider[] hittedColliders = Physics.OverlapSphere(transform.position, 10);
        foreach (Collider collider in hittedColliders)
        {
            // if you want to apply the damage only to players
            // if (!collider.CompareTag(GameCore.HITBOX_TAG)) continue;
 
            var damageable = collider.GetComponent<IGameDamageable>();
            if (damageable == null) continue;
 
            DamageData damageData = new DamageData()
            {
                Damage = 50,
                Direction = transform.position,
                GameActor = GameCore.LocalPlayer.GameActor,
                Cause = DamageCause.Explosion
                // see the other DamageData properties that you can use.
            };
 
            // send the damage to the hit box.
            damageable.ReceiveDamage(damageData);
        }
    }
```

****对物体造成伤害****
 
若要对玩家或机器人以外的 GameObject 造成伤害，只需在你的自定义脚本中实现 **IGameDamageable** 接口即可。
 
假设你有一个油桶，希望被子弹击中时受损，无需改动核心脚本，只要在自定义脚本中实现 **IGameDamageable** 接口并重写 **ReceiveDamage(...)** 函数，例如：
 
你的自定义脚本原本可能长这样：

```
public class TestHandler : MonoBehaviour
{
    public int Health = 100;
 
    public void ReduceHealth(int damage)
    {
        Health -= damage;
 
        if(Health <= 0)
        {
            // Destroy or wherever happens when run out of health
        }
    }
}
```

你需要实现 **IGameDamageable** 接口并重写接口函数 **ReceiveDamage()**，如下所示：

```
public class TestHandler : MonoBehaviour, IGameDamageable
{

    public int Health = 100;
 
    void IGameDamageable.ReceiveDamage(DamageData damageData)
    {
        ReduceHealth(damageData.Damage);
    }
 
    public void ReduceHealth(int damage)
    {
        Health -= damage;
 
        if(Health <= 0)
        {
            // Destroy or wherever happens when run out of health
        }
    }
}
```

这样就完成了。注意该对象必须带有碰撞体，才能被子弹命中。

> 烘焙方法见：
> https://docs.unity3d.com/Manual/occlusion-culling-getting-started.html（https://docs.unity3d.com/Manual/occlusion-culling-getting-started.html）

> **❓ 每个房间有玩家数上限吗？**
>
> 同一房间能容纳的玩家数没有固定上限。但每增加一名玩家都会增加服务端压力，也会占用本地客户端设备资源。超过一定人数后，游戏会开始出现卡顿，表现为帧率下降和网络延迟升高。
> 
> 出现性能问题的人数阈值取决于多种因素，例如运行平台、设备配置、网络状况等。
> 
> 使用默认配置测试取得参考基准，结果如下：
> 
> **PC** 配置为：
> *Intel i7 3.70GHz
> 16Gb 内存
> Nvidia GTX 1070*
> 
> 同房间 18 名玩家
> 中等画质
> 平均 60 到 80 帧
> 
> **移动端**：
> 使用三星 S8 Plus
> 
> 同房间 12 名玩家
> 使用针对移动端优化过的本作 *非默认场景*
> 平均 60 到 75 帧
> 
> 这些数据可供参考，但影响结果的因素很多，建议自行测试。

> **❓ 有 Photon 之外的网络方案吗？**
>
> 本作提供完整源码，你可以做任何改动，包括接入其他网络方案。
> 
> 但默认并不存在前端开关 *例如一键切换不同库* 来实现这件事。
> 接入其他网络库需要大量代码改动，把 Photon 的写法替换为对应 SDK 的写法，而且 Photon 的部分方法或功能在你的网络库中可能并不存在，或实现方式不同。

> **❓ 我可以自建独立服务器吗？**
>
> 可以。Photon 提供自建服务器方案 **Photon OnPremise** *即 Photon Server*。从默认的 Photon PUN 云端切换到它无需改动代码，只需搭建 Photon Server SDK 并在 PhotonServerSettings 中填写 IP。
> 
> 详见：Photon Server 资料（https://doc.photonengine.com/en-us/server/current/getting-started/photon-server-in-5min）

> **❓ 房间对其他玩家不显示？**
>
> 与他人联机测试时，你或某位测试者创建的房间有时不会出现在房间或服务器列表中，最常见的原因是你与测试者 **不在同一服务器区域**。
> 
> 在 MainMenu 或大厅场景的右下角有一个显示区域名称的下拉框，可用它选择并切换服务器。请确认你与所有测试者连接的是同一服务器区域。

### KnownIssues

本页列出本作的已知问题。这里关注的不只是缺陷或错误，也包括我们目前无法修复或规避的问题，以及 **影响本作开发流程的问题**。以下回答偏向开发者个人视角，供参考。

**抽象层**
 
对经验丰富的程序员来说，翻阅本作源码后很快会注意到的一点是，大多类几乎没有抽象层。这在实现或修改游戏功能时尤其成问题，因为唯一的办法是改动原始脚本，于是又引出另一个问题：你再也无法把本作升级到新版本，因为升级会覆盖你的改动。
 
那为什么会这样？为什么不写更整洁、可维护、可扩展、便于继承的代码？
这个问题需要一些背景，我尽量简短说明：
 
- 本作最初并非作为分发给其他开发者的游戏模板，它原本是一个个人项目，甚至算不上游戏，而是一个学习项目。当时的目标是先跑通功能，代码整洁度往后放。直到 2018 年作为游戏模板发布，核心代码的重构才开始，并且至今仍在进行。每次更新不仅加入新功能，也在用更整洁、支持抽象的代码改善既有功能，让模板更模块化、更便于程序员修改。
 
当然，这项工作远未结束。我很清楚这一点，但本作功能太多，要为现有功能提供更好的实现，或者至少在不改变行为的前提下让代码更易推断，工作量很大。而且开发人手有限，因此重写全部内容需要时间。

**URP、HDRP、TMP、输入系统支持**
 
Unity 在不断改进，我们也尽量采用其最新技术。Unity 发布的新特性会在将来取代现有方案，例如新的渲染管线 URP 与 HDRP、Text Mesh Pro、新版输入系统等。
 
但这些特性大多是在去年年中 *2020 年* 才脱离预览或测试阶段的。在此之前它们不推荐用于正式项目，因此本作并未采用。如今它们已可用于生产，正是开始使用的时机，当然这需要一定工作量。Text Mesh Pro 与新版输入系统的支持已列入后续更新计划。
 
那 URP 和 HDRP 呢？
本作已经支持它们，只是并非默认，需要手动转换项目。更多信息见本文档的通用渲染管线章节。

**所有游戏模式支持机器人**
 
本作用户另一个常问的问题是 **为什么机器人不是所有游戏模式都支持？**
 
答案可能让你失望：单纯因为工作量太大。
是的。人工智能本就是棘手的领域，再加上多人联机就更复杂。即便是本作这类基础机器人，开发也很费功夫。不过本作确实内置了多人 AI 射击系统，支持两个最常玩的游戏模式。问题在于其余模式都要求机器人按该模式的规则做出定制化行为，这部分复杂且工作量大，因此未包含在本作中。
 
这是否意味着其他游戏模式永远不会支持机器人？
不是，只是目前还没有排期。
